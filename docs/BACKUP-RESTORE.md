# Backup and restore

**Status:** No-key archive and automatic-by-default Android-managed backup experimental on `develop`; direct Drive API integration remains blocked. Updated 2026-11-04.
**Responsibility:** Defines backup experience, format requirements, transports, recovery and failure atomicity.
**Related specifications:** [Security](SECURITY.md), [Crypto design](CRYPTO-ARCHIVE-DESIGN.md), [Privacy](PRIVACY.md), [Storage](STORAGE-AND-RETENTION.md), [Contracts](NATIVE-CONTRACTS.md), [Testing](TESTING.md).
**Unresolved feasibility:** F-04–F-06 in [Decisions](DECISIONS.md); prototype format selected under ADR-031, but interoperability, resource behavior, provider durability and automatic-backup policy remain independently unqualified.

## Current beta override (ADR-073/ADR-074/ADR-079, 2026-11-07)

Current product backups require no remembered password/key. Public-package envelope profile 3 derives its wrapping credential from SHA-256 of ASCII `attention.stats`; anyone holding the file can decrypt or modify it. Storage-account access controls provide privacy, not this public credential. The earlier secret-key prototype remains historical evidence only and does not describe current product behavior.

The maintainer accepts automatic-by-default Android Auto Backup: Android controls the configured backup account and roughly nightly opportunistic scheduling after at least 24 hours, with a 25 MB transport quota. Our candidate uses a bounded 20 MiB plaintext / 100,000-record bound, requires API 28+, secure screen lock and transport client-side encryption, and excludes device transfer. Only a bounded logical snapshot is eligible; all live files, keys, preferences and grants remain excluded. Restore quarantines the one allowlisted archive for user preview; it never blindly restores the live database. Pending-restore admission includes the committed file and AtomicFile recovery/staging siblings (`.bak`/`.new`), so interrupted delivery cannot bypass the backup fence. Reads recover committed AtomicFile content; read, write and discard operations share a process lock. Discard must remove all siblings or report failure while keeping backup blocked; staging-only bytes are not accepted as a committed archive. See AS-058 for actual evidence. Direct Drive API integration remains blocked independently by F-05.

Logical version 2/schema 9 includes per-fact immutable ID/origin provenance and preserves it across replacement/re-export. It is not merge/sync; future deduplication/conflict/deletion fences follow ADR-050/ADR-074. Android system restore is disaster recovery, not an extension-sync transport. Current source does not accept the earlier unpublished version-1/schema-8 recovery-key archives in its no-key flow.


## Portable encrypted archive: MVP

AS-020/AS-058 use suite-1/profile-3 Tink framing with the public package credential above, logical version 2 and schema 9. Runtime quota is 20 MiB plaintext / 100,000 records; reject excess without omission. Supported history/configuration tables and per-fact origins are included; device keys, store metadata, source grants and live ingestion cursors are excluded. The candidate offers full-snapshot replacement, not selective scopes, summary-only export or merging. No key entry is required. Android's document picker handles explicit manual destinations; no app-created plaintext staging file.

Restore fully authenticates bounded owned ciphertext before parsing, checks strict records/JSON and exact columns/counts into an independently keyed encrypted staging store, previews record scope, offers current-data backup, then confirms a revision-bound transactional replacement. Failure before commit preserves live data; after durable commit report success even if UI/cache refresh fails. Collection, playback and protection are disabled after import, while physical grants remain current-device state. Activity cancellation closes staging; provider durability, process-death cleanup, resource limits, extended schema compatibility and the full acceptance suite remain qualification work. Source integration is not acceptance evidence.

The current full-snapshot export/import needs no product account or cloud API. Selective app/time/configuration scopes remain planned. Preview size, scope and known omissions. Generate a consistent snapshot at a known revision; do not copy an actively changing database/WAL as if it were a complete archive.

Use a documented versioned logical archive with authenticated encryption. Proposed manifest fields: format version, minimum reader version, schema/model revisions, creation UTC, snapshot generation/revision, data scope, entity counts, coverage, timezone representation and bounded crypto parameters. Sensitive manifest details live inside the encrypted payload; public header contains only necessary version/crypto framing. No provider token, device key, account email or raw recovery credential is included. [Security](SECURITY.md) owns algorithm review; no unreviewed cipher/KDF parameters become a shipping format.

ADR-031 and [crypto design](CRYPTO-ARCHIVE-DESIGN.md) define the prototype's 60-byte prefix, bounded wrapped keyset, Tink streaming payload, generated-key/optional-gated-passphrase profiles, strict logical record framing and quotas. An [isolated generated-key envelope fixture](CRYPTO-ARCHIVE-DESIGN.md#isolated-archive-envelope-result) now passes synthetic phone/readback/adversarial checks, with independently readable public vectors; that result applies to the historical profile-1 fixture, separately from the current profile-3 product jobs and logical parser. There is no compression or path-bearing file extraction. Authenticate the complete private ciphertext before history parsing, then parse a second authenticated pass into an encrypted staging database; require end record, final tag and physical EOF before preview. A valid prefix cannot authorize replacement. Exact entity encodings/migrations and supported summary scope still need AS-009/AS-020 review.

The current public package credential is reproducible on another installation and needs no user memory or old device Keystore. Verify recovery before advertising backup as ready. The earlier generated-secret/passphrase prototype is not the current UI or a source of secrecy guarantees for profile 3.

Export stages: preflight capacity → snapshot → bounded serialization → encryption → native staging → selected transport write → completion confirmation. Staging is private/no-backup and encrypted, cleaned on success/cancel and after crash. A provider accepting bytes does not necessarily mean remote durability; show the strongest confirmed state and uncertainty. Never overwrite the only known-good external archive before the new file is complete; provider-specific atomicity needs a capability check.

## Optional summary-only scope

Under [Retention](STORAGE-AND-RETENTION.md#user-configurable-summary-tiers), a person may choose detail or selected day/week/month/year facts independently from local pruning. A summary-only archive manifest declares metric/semantic/taxonomy revisions, units, dimensions, fixed zone/week start, covered/eligible/unknown partitions, retained sufficient statistics and omitted detail/resolution. It contains no fabricated chronology, purged content or implied source enablement. A summary export does not compact the local store.

Restore validates partition authority/non-overlap and sufficient-statistic bounds before replacing live history. Do not double count included detail and its summaries or expand yearly facts into monthly detail. Preview lost drill-down and coarse-deletion limits. Format versions explicitly support or reject these entities; no fallback can silently discard them. D-06 applies alongside all B-01–B-07 failures. This extension remains planned after the reviewed base encrypted archive implementation; AS-035's pure rollup preview is not backup/crypto code.

## Automatic Google-account experience

The accepted current route is Android-managed backup under the account selected in Android Settings, with no app password or app-controlled daily/weekly scheduler. On foreground entry, an unset device-local backup choice becomes on; saved on/off choices are preserved. Opening the app retries a timing request at most once per 24 hours, with a retry after clock rollback. Unsupported devices wait for prerequisites without losing the choice. Local erase saves off, so reopening does not re-enable backup. Pending Android restores block both requests and snapshot handoff until reviewed or discarded; request/transport handoff status must not imply confirmed cloud durability. Android scheduling is opportunistic, roughly nightly after at least 24 hours, never an exact promise. Account selection and provider copies are managed by the OS/provider. A future direct-Drive experience would need separate policy clearance, consent and transport qualification.

**Direct Drive integration is unverified and blocked pending policy clarification.** The current [Workspace API user data policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy) lists backup of app/user content from a developer's app among disallowed Drive-scope uses. Our intended use therefore conflicts with the published policy. Do not implement OAuth/upload or promise an appDataFolder exception without documented clarification applicable to this use case. No existing service's mechanism is assumed publicly reusable. F-05 requires dated authoritative clarification and review before choosing scopes, libraries or implementation.

Optional cloud backup transfers ciphertext and provider-visible metadata such as account, file size/name/timestamps and network request information. The developer receives neither. Local-only use stays complete without provider authorization. The provider's own storage/account policies and availability still apply.

## System-picker transport

Policy recheck (2026-11-03): [Drive terms](https://developers.google.com/workspace/drive/api/terms) require Google's express prior written consent for app-content backup, and the [Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy) lists it among disallowed Drive-scope use cases. F-05 stays blocked; no OAuth or API upload is implemented. The user's Drive request remains AS-028 and is not represented as satisfied by the manual file picker.

Android SAF can expose local or cloud-backed document providers and user-selected file access. See [Storage Access Framework](https://developer.android.com/guide/topics/providers/document-provider). Evaluate manual `ACTION_CREATE_DOCUMENT` and `ACTION_OPEN_DOCUMENT` for encrypted export/import without broad storage access. Treat provider behavior, URI-grant persistence, interrupted writes, quota and deletion support as per-provider capabilities.

Picker-backed export is not equivalent to automatic Drive backup. Selecting a cloud provider can cause that provider to upload the encrypted file and expose metadata to it; disclose this. A persisted URI grant does not resolve a provider policy question or guarantee background scheduling, account selection, atomic replace or upload completion. Manual picker transport needs its own verification alongside the separate Android-managed route; scheduled picker-backed destinations are an independent future evaluation.

## Restore state machine

1. Select a manual archive or an Android-delivered quarantined archive; use the public profile-3 package credential without asking for a password. Preflight file/expanded-size limits and free space without changing live data.
2. Validate framing and bounded KDF parameters, authenticate/decrypt into private staging, validate manifest/entity counts/references and supported versions. No rule or imported field can execute code.
3. Migrate the staging store through supported migrations. Reject future/incompatible formats. Produce a preview of replacement scope, age, omitted data and estimated size.
4. MVP restore is explicit **replacement**, not merge. Offer a current-data encrypted export before replacement. Require user confirmation of the concrete preview. This is an application UX requirement, not a request for repository-work approval.
5. Acquire native write barrier, pause ingestion/interventions, transactionally commit validated state or an interruption-safe generation swap, rebind database handles and increment generation. Retain a rollback-safe old generation until commit durability is confirmed.
6. Rebuild aggregates, invalidate cursors, preserve current device grants separately, and leave imported source consent and protection disabled until the person reviews/reactivates them. Imported data never grants current permissions or silently enables tracking. Resume only explicitly chosen current configuration.

Wrong credentials, corrupted tags/payloads, incomplete archives, cancellation, interrupted writes, insufficient storage, invalid references and unsupported versions must leave existing live data unchanged before the commit point. After a durable commit, report committed state even if UI delivery failed; replaying a job cannot import twice. Never delete the current store to “make room” for an import.

## Android automatic backup and transfer

Sensitive history, configurations, MMKV preferences, staging, keys and tokens must not leave through undocumented Android defaults. Under ADR-073/ADR-079, set `allowBackup=true` only with the custom logical-snapshot agent and a single-file cloud include requiring protected transport. Exclude every device-transfer domain. The explicit cloud include excludes all other default files; keep pending restore/staging/key wrappers in no-backup paths. Govern cross-platform transfer rules too where the target supports them. Avoid debug-only overrides leaking into release manifests.

Android documentation warns that some manufacturers may still allow device transfer when only allowBackup is false; explicit rules and real-device tests are necessary. See [Android Auto Backup](https://developer.android.com/identity/data/autobackup). The release gate tests merged manifest, database/WAL, shared preferences, files, MMKV locations, no-backup files, cloud restore and device transfer. Unexpected transfer blocks release. AS-058 is the separately authorized Android framework route; it does not clear F-05 for direct Drive API use.

Acceptance B-01–B-07 and S-01 in [Testing](TESTING.md) includes fresh-device recovery, wrong credentials, corruption, interruption at each stage, format compatibility, permission reactivation and preservation of existing history. Direct-Drive UI must remain blocked/unavailable; Android-managed status must report only its actually verified state.

The [November 11 isolated phone trial](IMPLEMENTATION_LOG/2026-11-11.md) passes 17 synthetic source-key-loss/recovery checks: the unavailable source key cannot silently recreate history, while a profile-3 archive restores into a separately keyed destination and survives reopening with fact ID/origin/totals retained and sources disabled. Corruption preserves the destination. This does not qualify Android framework reinstall recovery, maximum logical history, or concurrent restore-delivery versus backup admission/handoff; those gates remain open under AS-058.

ADR-050 lifetime history, immutable event/origin provenance, future merge/deletion semantics and rebuildable calendar summaries are defined in [Storage and retention](STORAGE-AND-RETENTION.md#lifetime-event-history-and-future-multi-origin-merging). These are design obligations; current preview storage/aggregate/restore limits remain explicit.
