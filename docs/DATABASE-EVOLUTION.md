# Database durability and behavior-history evolution

**Status:** Accepted engineering direction under ADR-106; schema-9 static review and scoped failure checks exist, broader implementation/qualification remains open. Updated 2026-11-16.
**Responsibility:** Turns the maintainer's continuous local behavior-history requirement into ordered database, migration and recovery work; does not replace entity or metric semantics.
**Related specifications:** [Models](DATA-MODELS.md), [Storage](STORAGE-AND-RETENTION.md), [Analytics](ANALYTICS-SPEC.md), [Metrics](METRIC-CATALOG.md), [Backup](BACKUP-RESTORE.md), [Security](SECURITY.md), [Tracker](FEATURE-TRACKER.md).
**Unresolved feasibility:** Reliable source identity/timing, historical migration, crash/ENOSPC durability, lifetime capacity, Android recovery and F-04/F-05 remain open. No schema can guarantee recovery from every hardware/key/storage failure or reconstruct observations that were never available.

## Maintainer requirement — 15/11/26

The database is the product's core. Preserve useful enabled digital behavior evidence for later personal pattern exploration, analytics, intelligence and predictions, even when current screens use only a subset. This includes ordered behavior and context, not just daily totals. Keep processing local and backup under the person's choices. Extend existing AS-009/AS-010/AS-014/AS-020/AS-038/AS-058/AS-062 obligations; do not open a separate history store or silently enable collection.

“Every data possible” means the useful, supported, disclosed data families the person enables. Make maximum supported detail an explicit progressively disclosed choice, with measured storage/resource costs and exclusions. It never grants unrestricted screen/input/message capture. Adding schema capacity does not add source availability. New families need their own source/privacy/consent/quality/deletion/backup tests; preserve old choices and historical unknowns. Retain enabled detailed facts until explicit deletion or a separately previewed retention choice. No automatic reduction to totals, background pruning or invented historic backfill.

## Production compatibility baseline — ADR-108

The maintainer clarifies on 16/11/26 that earlier builds were test-only and the next release establishes the first public production baseline. Supporting those test schemas or transferring the debug package into production is optional; preserving the installed phone data during development remains required. Existing migration fixtures are useful engineering regressions, not a promise to support all pre-production versions publicly. Freeze the actual first-production schema/artifact at release. Thereafter, each new release must preserve earlier production data/choices through direct or chained migrations, including skipped app updates. Do not pre-create speculative fields or require today's binary to read unknown future schemas; reject unsupported newer/downgrade opens without deletion. Package/signing continuity and separately qualified backup recovery are independent requirements. [Decision](DECISIONS.md#first-public-production-data-baseline--adr-108--2026-11-16).

## Current review and material gaps

The [static inventory](evidence/database-evolution-review.json) is bound to source hashes, not a phone-history read. Current Room schema 9 has 14 tables, retained schema snapshots 1–9, eight adjacent auto-migration declarations, a serialized native owner, device-key wrapping and encrypted WAL mode. The archive explicitly includes 12 tables plus per-fact origins; device metadata stays local. Facts and the usage query cursor commit together. These are useful foundations, not full migration/durability acceptance.

| Gap found in current source | Consequence and next requirement |
|---|---|
| Exported schemas and auto-migration declarations do not establish an every-old-version data-preservation result | Seed every historical schema and open through the actual current production migration path; compare meaningful rows, defaults, IDs, provenance, keys and query results after reopen. |
| `AppUsageEvent` stores only ID, consent epoch, package, wall time and event kind | Future exact event chronology/timezone/boot/multiplicity cannot be recovered from those fields. Add qualified evidence prospectively; mark migrated history unknown rather than deriving old zones/elapsed clocks from today's device state. |
| Usage replay key hashes epoch/time/kind/package | Identical tuples collapse; it supports current overlap estimation, not proven exact action/launch multiplicity. Qualify source ordering/identity and replay reconciliation before changing keys. Rehashing old rows cannot recover missing events. |
| Playback is accumulated on `Exposure`; behavior sessions and many facets are memory-only or derived | Later segment/seek/pause/return analysis cannot recover an unrecorded trace. A separately admitted compact typed evidence stream is needed where the source actually exposes it. Do not store every accessibility poll. |
| Only Exposure declares a SQL foreign key; FactOrigin is polymorphic | Validate owner-enforced relationships and delete/import lifecycle directly; add feasible foreign keys, uniqueness and domain constraints through preserving migrations after auditing legacy exceptions. Do not add guessed relationships or erase invalid legacy rows silently. |
| Archives are bounded to 20 MiB plaintext/100,000 records; current reader requires logical v2/schema9 | Lifetime local retention does not imply complete lifetime backup. Reject over-limit exports without omission; qualify bounded streaming/chunking, multi-generation recovery and logical-version adapters before advertising larger capacity. |
| Physical cancellation and SQLite page-cap FULL checks pass only their named scope | Actual process kill, fsync/checkpoint behavior, filesystem ENOSPC, migration interruption, concurrent owner recovery and framework reinstall remain release gates. |

## Evidence to preserve for behavior understanding

[Metric definitions and admission](METRIC-CATALOG.md) remain authoritative. Every enabled metric must trace to durable source evidence or declare itself a non-recomputable derived observation. Add typed domain tables only as admitted families arrive; the following is a design checklist, not current collection support.

| Evidence family | Useful retained details | Honest interpretation |
|---|---|---|
| App/device sessions and switches | Admitted foreground/background, screen/lock boundaries, app/profile reference, sequence/session links, start/end evidence and gaps | Reconstruct visits, switching, time-of-day/week and session length; censored ends and unobserved intervals remain uncertain. |
| Short-video/feed behavior | Encounter/episode IDs, route, type/ad facet, first/last observed times, qualified return/revisit evidence and detector version | Study visit length and encounter sequences. A transient node/page key does not establish enduring content identity or distinct content. |
| Qualified playback | Compact evidenced playing intervals, numeric position/duration when available, observed pause/buffer/seek/discontinuity reasons and consent epoch | Distinguish on-screen dwell, confirmed playback, observed completion and repeated viewing. Never generate progress from wall time. |
| Supported interactions | Bounded typed action, event time, context reference, evidence source, attempt versus observable outcome and unknown reason | Click intent does not establish server success, a submitted comment, purchase or social relationship. Never retain private typed text. |
| Notifications/network/other catalog families | Allowed metadata lifecycle/attribution epochs, canonical counters, timing, quality and explicit consent | These families remain individually gated. Bytes are not content; notification updates are not fresh arrivals or proof of reading. |
| Protection and intentional behavior | Rule/config revision, eligibility/trigger, actual display result, user choice, override scope/expiry, focus/break start/end and failure reason | Describe the observed response to an offered boundary; a missing response is not refusal or motivation. |
| Optional reflection | Separately entered, user-owned bounded annotations/goals and their revision/consent | Self-report is distinct from observed behavior; no inferred mood/diagnosis or hidden questionnaire. Separate sensitive retention/deletion rules are required before implementation. |
| Observation health | Coverage, pause, unavailable/permission/source-loss reasons and temporal scope | Distinguish no observed activity from no observation. Missingness is essential prediction context. |

## Schema and ingestion contract

Use one encrypted authoritative Room store with typed domain facts and bounded repository APIs. Shared observation metadata must have explicit semantics: immutable fact ID and origin; event-kind/payload semantic revision; source/app/profile/surface when established; event and receipt UTC time; source order/ordinal when established; elapsed time with boot provenance only when available; original zone/offset with provenance; consent/config/detector revisions; and quality/coverage references. Unknown fields stay explicitly unknown. These are target fields, not authorization to manufacture them on existing rows.

A shared fact header plus typed child tables is a candidate for new families, not a required immediate rewrite of existing facts. Prototype join/index/write amplification and compare with metadata columns on each domain table before selecting a physical layout. If adopted, header and typed payload commit together; every fact has exactly its admitted payload and deletion route. Avoid arbitrary JSON/EAV dumps, unbounded generic payloads and one column per speculative feature. Existing bounded protection JSON remains until an independently justified migration. Versioned optional extensions need an allowlisted bounded codec; an unknown semantic payload cannot become silently accepted analytics.

Separate immutable source observations, revisioned corrections/reductions, user configuration, durable retained summaries and disposable query/model caches. A later classifier must not overwrite the original evidence or make today's taxonomy appear historically observed. Corrections need provenance and deterministic conflict policy; they cannot bypass deletion fences. Predictions reference input revision/window/coverage and model version; invalidation follows deletion, consent/representation changes and corrected evidence. No future training dataset may silently retain deleted behavior.

Use bounded native batches and one serialized write authority. Persist admitted facts, dedup/reconciliation state, query receipts/cursors, revisions and rebuild markers atomically; acknowledge only committed results. Replays need stable qualified identities, not timestamp-only guesses. Handle bounded BUSY/full/key/corrupt failures without resetting history or advancing progress. Define queue bounds and backpressure; non-replayable dropped intervals must become explicit degraded coverage rather than fabricated continuity. Preserve admitted semantic transitions/segments, not redundant high-frequency samples.

Choose indexes from real bounded queries: time+stable ID, app/source+time+stable ID, episode/sequence and evidence/rebuild references. Verify query plans and write cost before adding overlapping indexes. Never infer cross-boot order solely from elapsed time or impose false uniqueness on source timestamps. Use database constraints where expressible and owner validation for cross-row temporal/non-overlap invariants; test both. Current `-1` unknown sentinels require explicit compatible decoding; any nullable-value/reason conversion is a real migration, not a Kotlin-default change.

## Effective durability policy — ADR-107

Physical candidate `b118f85`/`bb9a54a` passes 123 bounded settings/constraint/integrity/reopen checks plus the 301-check historical regression, raw -1; [runtime evidence](evidence/database-durability.json). Writer probes are transactional; final sampled reader/writer synchronization is 2 and foreign keys are 1. The earlier NORMAL finding and failed reopened-reader candidate remain recorded. This is policy and bounded recovery evidence, not hardware power-loss acceptance.

16/11/26 physical inspection exposes NORMAL synchronization on the existing schema-9 opener. Preserve this finding separately from the strengthened candidate: WAL consistency and successful reopen alone do not establish power-loss commit durability. Raise the pinned Room configuration command to FULL on the primary writer in the owned driver, before migrations as well as ordinary writes. Configure foreign keys through the native database pool so later handles inherit enforcement. Native read-only handles may retain NORMAL; writer synchronization must be measured inside a write transaction. An open callback is insufficient because it follows migrations and does not configure every later connection. This compatibility adapter requires effective reader/writer regression checks on dependency/configuration changes; it is not a general arbitrary-SQL policy. [Decision](DECISIONS.md#sync-committed-history-to-the-wal--adr-107--2026-11-16).

## Migration and durability qualification before expansion

16/11/26 runtime checkpoint: the test-only `historicalMigrations=true` production-opener harness passes 301 physical API36 ARM64 checks for populated schemas 1–9 to schema 9 and separate fresh defaults. Every original column, added SQL default, disabled choices, semantic queries, imported origins, key identity and every-table reopen pass. Loader/parser failures were corrected and retained; owned cleanup and fresh baseline/reverse mappings match. See [runtime evidence](evidence/historical-migrations.json) and the earlier [build-only checkpoint](evidence/historical-migrations-build.json). This supplies bounded parts of steps 1–2 below; adjacent intermediate targets, representative bounds, unsupported-version rejection, effective constraints, interruption and durability remain open.

1. Preserve schemas 1–9 and build an isolated SQLCipher fixture for each supported start version. Exercise adjacent upgrades and each start-to-latest chain through the production opener. Include populated facts/configuration, non-default choices, imported origins, empty/null/unknown values, and representative bounds. Compare constraints, values, semantic projections, local metadata and encrypted reopen; Room schema validation alone cannot prove row preservation.
2. Define fresh-install defaults separately from migrated defaults. New source/detail stays disabled; do not rewrite historical unknowns or reactivate grants/rules. Reject unsupported future/downgrade paths without destructive fallback. Local Room version, archive wire version and metric/reducer semantic revision evolve independently.
3. For complex changes use additive expand/backfill/validate/activate where feasible. Persist backfill progress and deletion/consent fences; publish a new representation only after validation. Small DDL steps remain transactional; resumable multi-transaction work needs explicit job state and dual-read/write rules. Measure temporary space/WAL and keep the original authoritative representation until activation is durable. No blanket claim of an atomic multi-stage migration.
4. Inject interruption/full/corrupt/key-loss at meaningful boundaries with wholly synthetic stores. Prove precommit preservation, postcommit reopen, idempotent recovery and truthful owner/UI delivery. Read back effective foreign-key/journal/synchronous/checkpoint settings on the actual SQLCipher driver and inspect its embedded SQLite version/security fixes. WAL mode alone is not proof of power-loss durability; do not weaken synchronous policy to win a benchmark.
5. Qualify bounded queries, ingestion, rebuild and backup against the declared 1M/10M/50M-event datasets as feasible; record failed budgets and device/storage conditions. Keep all-history cache/UI memory bounded. Continue resource/long-run tests separately; the seven-day baseline is still unstarted.

Android documents exported schema and migration testing separately from migration declarations in [Room migration guidance](https://developer.android.com/training/data-storage/room/migrating-db-versions). The project's Room 3/SQLCipher execution remains subject to actual compatibility checks. SQLite documents [foreign-key enforcement](https://www.sqlite.org/foreignkeys.html) and [WAL/checkpoint/durability tradeoffs](https://www.sqlite.org/wal.html); reviewed 15/11/26. These references support the protocol, not a production pass.

## Recovery and delivery order

Honor existing saved Android-backup on/off choices and disclosed defaults under ADR-079. A richer maximum-detail selection never enables backup by implication. Android manages the selected account and schedule; direct Drive API/OAuth stays blocked by F-05, independently of permitted Android transport. Existing public-package profile-3 archives are readable/modifiable by their holders; schema richness does not strengthen confidentiality. Broader behavior backups require a separate threat/privacy review before promising them as private archives. Existing grants, keys, source enablement and protection activation are never imported as live authority.

Backups must preserve admitted facts, origins, uncertainty, units and semantic versions. Exclude device keys/cursors/grants and rebuildable model caches; exact portable coverage belongs to a manifest and preview. Prove independent-install recovery, compatible archive upgrades, failed-write preservation, stale snapshot/deletion behavior and quota handling. Android's current quota and the application's lower archive limits need explicit scale qualification, never silent truncation. No recovery-as-sync claim or hidden Drive fallback.

First close the current preservation foundation: historical migration matrix, effective durability settings, owner recovery and bounded integrity checks. Then introduce the prospectively qualified observation/behavior metadata needed by current collection; validate the physical layout and portable format together. Add new behavior families only through their existing AS/source/consent gates. Incremental lifetime archive/retention/rebuild work follows its dependencies. This direction prioritizes durable evidence without replacing the publishing phase with speculative mass collection; remaining preservation gates stay HOLD.
